### <a name="_3bfxc9a45514"></a>**Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
|---|------------------------------|----------|----------|
| 1 | Новый клиент, Сайт, Система кол-центра, Менеджер кол-центра | Подача заявки на депозит через сайт | 1. Клиент заходит на сайт и видит список доступных депозитов с актуальными ставками.<br>2. Клиент входит в интернет-банк и видит список депозитов с актуальными и персонализированными ставками.<br>2. Клиент указывает счет, сумму, подает заявку (шифрованный трафик).<br>3. Подтверждение операции СМС-кодом через СМС-шлюз.<br>4. Заявка передается в АБС для обработки менеджером бэк-офиса.<br>5. Менеджер подтверждает условия в АБС.<br>6. Клиент получает СМС-уведомления о подтверждении ставки и открытии депозита. |
| 3 | Бэк-офис (депозиты и кредиты), АБС | Управление ставками по депозитам | 1. Сотрудники бэк-офиса депозитов и кредитов просматривают/обновляют ставки (сейчас в XLS, предлагается перенести в АБС).<br>2. Расчет ставок на основе данных о кредитном риске (интеграция внутри АБС).<br>3. Согласование специальных ставок без прямого доступа к данным друг друга (через АБС или промежуточный слой). |
| 4 | Все системы (Сайт, Интернет-банк, АБС, Система кол-центра) | Интеграция и передача данных | 1. Передача заявок с сайта в систему кол-центра.<br>2. Передача заявок из интернет-банка в АБС (асинхронно, чтобы избежать перегрузки).<br>3. Отправка СМС-уведомлений через шлюз. |


### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| **№** | **Требование** |
|---|------------|

| 2 | Шифрование трафика (HTTPS) для передачи чувствительных данных на сайте и в интернет-банке. |
| 3 | Отклик операций в миллисекунды; оптимизация загрузки справочных данных (кэширование ставок). |
| 4 | Горизонтальное масштабирование интернет-банка; вертикальное для АБС; избегание прямого доступа к API АБС. |
| 5 | Использование существующих технологий (MS SQL, Oracle, .NET, Java, React.js); Kafka для очередей на перспективу. |
| 6 | Микросервисная архитектура для модуля депозитов в интернет-банке; совместимость с текущими платформами. |
| 7 | Удобный интерфейс с корпоративным дизайном (цвета, брендинг); документация для расширения. |
| 8 | Реализация силами банка без доработки ядра подрядчиком; наличие экспертизы в технологиях. |

### <a name="_qmphm5d6rvi3"></a>**Решение**
[Диаграмма контекста](./mvp_online_bid_c4_context_diagram.wsd)
[Диаграмма контейнеров](./mvp_online_bid_c4_conteiner_diagram.wsd)

Для MVP предлагаю интегрировать существующие системы с минимальными изменениями, основной упор на онлайн-подаче заявок и ручной обработке в бэк-офисе. Логика выбора:
- **Функциональные аспекты**: MVP сохраняет ручную обработку в АБС для снижения рисков, но добавляет онлайн-интерфейсы для привлечения клиентов. Интеграции асинхронные (через Kafka или аналог) для избежания перегрузки АБС, все таки система старая и важная.
- **Нефункциональные аспекты**: Используем текущие технологии (например, React.js для фронтенда сайта/интернет-банка, Oracle для АБС) так как этими компетенциями обладает наш персонал. Шифрование трафика (HTTPS) для безопасности. Масштабирование: горизонтальное для новых микросервисов в интернет-банке.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**Монолитное расширение интернет-банка без микросервисов**: Добавить функционал в существующий монолит. Но, это снижает масштабируемость и противоречит перспективе на Kafka и микросервисы.

### <a name="_bjrr7veeh80c"></a>**Недостатки, ограничения, риски**

-Зависимость от подрядчиков для обновлений ядра интернет-банка/кол-центра может замедлить итерации;

-Ручная обработка в бэк-офисе сохраняет задержки (до 20-60 мин);

-АБС масштабируется только вертикально, что ограничивает рост трафика; текущая интеграция интернет-банка с БД АБС прямая — риск перегрузки без асинхронного слоя;

-Безопасность: если шифрование не настроено правильно, риск утечек ПД;
